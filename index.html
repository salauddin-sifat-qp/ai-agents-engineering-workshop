The execution boundary

Model requests.
Application decides.

Model
Requests a tool call. Never runs it.
Application
Validates, classifies, maybe asks a human.
Tool
Runs. Returns a result.
Model
Receives the result, decides what's next.

Example 03

The agent loop

while (!finished) {
  response = model(messages, tools)

  if (response.toolCalls.length) {
    for (call of response.toolCalls)
      messages.push(executeTool(call))
  } else {
    return response   // unless finish_reason is "length"
  }
}

Everything else in five sessions is a refinement of this.

Two safeguards, two failures

Bounding the loop

MAX_ITERATIONS
A model that never stops asking for tools, until your budget is gone.
TOOL_TIMEOUT_MS
One hung tool call stalling the whole run, with no output at all.

Hitting the cap is information: the task was too big, the tools too weak, or the prompt too vague. And a timeout stops the waiting, not the tool — it may still be running.

What it costs

Append-only,
for a reason

12 turns, 2,000-token prompt, +500 tokens a turn
final context:        7,500 tokens
total billed:        57,000 tokens   # every call re-sends the past

Cost is closer to quadratic in turns than linear. Example 04 prints the real numbers, from the provider's usage field.

Prompt caching is the mitigation: providers cache the prefix and charge a fraction to re-send it. Anthropic marks breakpoints explicitly, Gemini caches implicitly.

Edit an earlier message and you invalidate the cache from there on. That's why compaction is a rare, deliberate event.
More calls, more 429s

Two kinds of retry

Transport · provider.ts
429, 5xx, dropped connection, timeout. The harness decides. Backoff, Retry-After, jitter. The model never sees it.
Semantic · the loop
A tool returned { ok: false }. The model decides: try again, or take another route. Session 5.

A rate limit carries nothing the model can act on. A failed tool carries exactly what it needs. Different layers, on purpose.

Good:

You can't write a policy for executeAnything. A policy needs to know what a tool does, and it does anything.

Example 05 · the real one

edit_file — four rules

Read before write
Editing an unread file is editing a remembered file.
Exactly one match
Zero and many are different errors with different fixes.
Failed match is an error
Never a silent no-op. The worst case is the agent reasoning on from a fix that never landed.
Return a diff
A human must be able to review it without opening the file.

And that's the simple version

What pi's edit tool adds

Line endings
CRLF normalised before matching, restored on write.
Invisible BOM
Stripped before matching. The model can't see it.
Fuzzy fallback
Trailing spaces, smart quotes, Unicode dashes normalised if the exact match fails.
Many edits, one call
Each matched against the original file. No overlaps.
Per-file queue
Parallel edits to one file can't race.

Every line is a bug someone hit in production.

Prompts shape tendencies.
Code sets limits.

Example 06

Compaction

[system] [task] [..... summarised .....] [recent turns verbatim]
System + task stay verbatim
Lose the task and the agent forgets what it was doing.
Recent turns stay verbatim
That's where the live work is.
The middle gets summarised
That's where the bulk and the redundancy are.

"Recent" is a size, not only a count: one huge result kept verbatim and compaction fires again every turn.

Truncation deletes. Compaction remembers, in less space.
The bug everyone hits once

Orphaned tool results

assistant: tool_call  id=abc   <- cut by compaction
tool:      result     id=abc   <- now an orphan
                               -> provider rejects the whole request

Cut the middle out and you can strand a tool result whose call is gone. Most providers reject the entire request. Rule: never cut between a call and its results.

Persistence

Save every turn,
not at the end

.session/transcript.jsonl   # one message per line, appended, never rewritten
                            # compaction is an entry, not an overwrite

pnpm 06          # Ctrl-C partway through
pnpm 06:resume   # picks up mid-task
A session you can only resume after a clean exit is a session you cannot resume. Crashing is exactly when you want it.
Your own tool does the same

Open its session file

ls ~/.pi/agent/sessions/          # pi   (Claude Code: ~/.claude/projects/)
tail -n 3 <session>.jsonl | jq -c '{type, id, parentId}'
grep -c '"type":"compaction"' <session>.jsonl

One entry per line. Compaction is an entry, not an overwrite. Every entry has a parentId, so a session is a tree: that's why /tree and /fork can go back without losing anything.

So you recognise them

What we didn't build

Streaming & cancel
Tokens arrive as they're generated; Esc aborts the request and the running tool.
Sandboxing
The OS, not the prompt, limits what a shell command can touch.
Stale reads
Refuse an edit if the file changed since it was read.
Hooks, skills, todo lists
Code at lifecycle points; instructions loaded on demand; a plan the model keeps.
A2A
MCP is agent-to-tool; A2A is agent-to-agent across a network. IBM's ACP merged into it in 2025.
Learn the problems, not the spec names. The problems are stable; the acronyms are not.
